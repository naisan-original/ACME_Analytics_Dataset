# ACME Analytics semantic model (Apache Ossie / OSI)

> **Synthetic data.** ACME Analytics is a fictional company, and every record in this dataset was generated by a program. Real company names appear for realism only. See the main README before you use it.

This folder describes the dataset as a semantic model in [Apache Ossie](https://github.com/apache/ossie) format. Ossie was called **Open Semantic Interchange (OSI)** until July 2026. It is a vendor-neutral YAML format for tables, joins and metric definitions, so BI tools and AI agents can share one definition of "ARR" instead of each guessing.

## Which file to use

| File | Spec version | Use it when |
|---|---|---|
| `acme_analytics.ossie.yaml` | `0.3.0.dev0` (current draft) | You use a current Ossie converter or tool. Recommended. |
| `acme_analytics.osi-0.1.1.yaml` | `0.1.1` (only released version) | Your tool reads the original OSI format, with models wrapped in `semantic_model:`. |

Both files hold the same model. The released format has no data types. The draft file writes each expression twice: in the portable `sql` form the spec prefers, and as `ANSI_SQL` for converters that still only read that form.

**Version note.** Ossie is still incubating and its draft changes often. On 2026-11-09 the draft was renamed from `0.2.0.dev0` to `0.3.0.dev0`, and most [reference converters](https://github.com/apache/ossie-converters) still check for `0.2.0.dev0`. If a converter rejects the version, change the `version:` line in the YAML to `version: "0.2.0.dev0"`. Nothing else needs to change: the edited file passes the `0.2.0.dev0` schema.

## What's in the model

- **8 datasets**, one per CSV. Each `source` is a placeholder, `acme_analytics.public.<table>`, because tools such as Snowflake require a full `database.schema.table` name. Load each CSV as a table named after its file (for example `fct_account_product_month.csv` becomes `fct_account_product_month`), then replace `acme_analytics.public` with your own database and schema.
- **15 relationships**, all many-to-one from a fact table to a dimension. `dim_employee` is joined twice from the main fact table, once as the Account Executive and once as the Customer Success Manager.
- **27 metrics**, including ARR, customers, API share, weighted usage estimates, bookings and sentiment.
- **AI context**: instructions, synonyms and example questions, so an agent knows that ARR is a monthly snapshot, that the fiscal year ends October 31, and that `region = 'NA'` means North America.

Deliberately left out:

- **No fact-to-fact joins.** Joining two fact tables row by row inflates totals. Total each one to account, product and month first.
- **No joins on descriptive months.** `customer_since_month_id`, `churn_month_id`, `hire_month_id` and `termination_month_id` are mostly blank and are not linked to `dim_month`.

## Limits of the format

Ossie metrics are single aggregate expressions. Three things in this dataset need more than that:

1. **Snapshot measures.** ARR, MRR, seats and active users can't be added up across months, and Ossie has no "last value in period" aggregation. The model provides `fiscal_year_end_arr`, `fiscal_quarter_end_arr` and `fiscal_year_end_customers`, which read only the period's last month. For other periods, filter to one month.
2. **GRR and NDR** compare each account with itself 12 months earlier, which no single aggregate can do. Use the SQL below.
3. **Active contracts in a month** need a range join (`start_month_id <= month <= end_month_id`). The `contracts` relationship to `dim_month` uses the start month, so it slices bookings.

### GRR and NDR

GRR caps each account at its ARR 12 months earlier, so expansion doesn't count. NDR includes expansion. Both cover the accounts that were paying 12 months earlier. FY21 has no prior year in the data.

```sql
WITH account_month AS (
    SELECT account_id, month_id, SUM(arr) AS arr
    FROM fct_account_product_month
    GROUP BY account_id, month_id
),
cohort AS (
    SELECT dim_month.fiscal_year,
           earlier.arr AS start_arr,
           COALESCE(later.arr, 0) AS end_arr
    FROM dim_month
    JOIN account_month AS earlier
      ON earlier.month_id = dim_month.month_id - 100
    LEFT JOIN account_month AS later
      ON later.account_id = earlier.account_id
     AND later.month_id = dim_month.month_id
    WHERE dim_month.month_id % 100 = 10
      AND earlier.arr > 0
)
SELECT fiscal_year,
       100.0 * SUM(LEAST(end_arr, start_arr)) / SUM(start_arr) AS grr,
       100.0 * SUM(end_arr) / SUM(start_arr) AS ndr
FROM cohort
GROUP BY fiscal_year
ORDER BY fiscal_year
```

## How it was checked

`uv run python tools/semantic_model.py --check` regenerates both files and then:

- validates each file against the official JSON schema for its version
- confirms every field matches a CSV column, every primary key is unique, and every relationship has no orphaned keys
- runs all 27 metrics as SQL against the CSVs with DuckDB
- confirms that year-end ARR, year-end customers and the GRR and NDR query above match the dataset's answer key

Both files also pass the validators in the official Ossie repository: the current draft validator for `acme_analytics.ossie.yaml` and the 0.1.1 validator for `acme_analytics.osi-0.1.1.yaml`.

The Snowflake reference converter (`apache/ossie-converters`) converts the draft file, with its version set to `0.2.0.dev0`, to a Cortex Analyst semantic model. All 8 tables, 86 fields, 15 relationships and 27 metrics come through, along with their synonyms. Snowflake's format has nowhere to put the AI instructions, so the converter drops them.
